# 微前端拆分评估报告

> **评估日期**: 2026-05-30 | **评估人**: 架构诊断团队
> **背景**: 当前为单体 SPA，Manifest 系统已为微前端预留扩展接口

---

## 一、现状分析

当前架构具备微前端就绪条件：
- **Manifest 插件化系统**：`src/modules/manifest-loader.js` 支持动态注册 Section/CMS/Routes
- **扁平 Provider 层级**：8 个独立 `provide()` 无嵌套，天然适合跨应用状态共享
- **CSS Modules 严格隔离**：无全局 class 污染风险

**当前单体 SPA 的瓶颈**:
- 构建产物随功能增加线性膨胀（当前 chunkSizeWarningLimit 已设 500KB）
- 15 个首页 Section + 24 个路由页面全部打包在同一 Bundle
- 任何页面的 bug 修复都需要全量重新构建和部署
- 多团队协作时，代码冲突概率高

## 二、拆分策略

### 2.1 按业务域拆分（推荐）

```
┌─────────────────────────────────────────┐
│           基座应用 (Shell App)            │
│  - NavBar / Footer / 全局状态 / 路由编排   │
│  - 共享组件库 (Button/Modal/IconSprite)   │
├─────────────────────────────────────────┤
│  子应用 A: 营销门户 (Marketing Portal)     │
│  - HomePage + 15 Sections                 │
│  - 产品/方案/案例/资源 列表+详情           │
├─────────────────────────────────────────┤
│  子应用 B: 内容社区 (Content Community)    │
│  - BlogList / BlogDetail                  │
│  - Forum / ForumTopic                     │
├─────────────────────────────────────────┤
│  子应用 C: 用户中心 (User Center)          │
│  - Profile / AuthModal                    │
│  - 招聘相关页面 (Careers/JobDetail)        │
├─────────────────────────────────────────┤
│  子应用 D: 关于我们 (About Us)             │
│  - About / Team / Contact / Partners      │
└─────────────────────────────────────────┘
```

### 2.2 技术方案对比

| 方案 | 实现方式 | 优缺点 | 推荐度 |
|------|---------|--------|--------|
| **Module Federation** | Webpack/Vite 模块联邦，运行时加载远程模块 | ✅ 共享依赖、无缝集成<br>❌ 构建工具耦合、配置复杂 | ⭐⭐⭐⭐☆ |
| **qiankun** | 基于 single-spa 的阿里微前端框架 | ✅ 成熟、支持 JS Sandbox<br>❌ 侵入性较强、DOM 隔离有开销 | ⭐⭐⭐⭐☆ |
| **Web Components** | 各子应用封装为 Custom Elements | ✅ 标准原生、框架无关<br>❌ 通信复杂、样式隔离需额外处理 | ⭐⭐⭐☆☆ |
| **Iframe** | 传统 iframe 嵌套 | ✅ 完全隔离<br>❌ 体验差、SEO 不可索引 | ⭐☆☆☆☆ |

**推荐**: **Module Federation (Vite)**。理由：
1. 当前已使用 Vite 8，原生支持 Module Federation 插件
2. Vue 3 组件可直接作为远程模块暴露和引用
3. 共享依赖（vue, vue-router）只需加载一次

## 三、迁移路线图

### Phase 1 — 基座建设（2 周）
- [ ] 将 `NavBar` / `Footer` / `IconSprite` / 全局样式提取为独立 `shell` 包
- [ ] 共享状态（i18n/theme/auth）封装为跨应用可用的 Composables 库
- [ ] 配置 Vite Module Federation 插件

### Phase 2 — 首个子应用试点（2 周）
- [ ] 选择 **用户中心** 作为首个拆分目标（交互相对独立，路由简单）
- [ ] 验证跨应用路由跳转、状态共享、弹窗层级

### Phase 3 — 批量拆分（1 个月）
- [ ] 拆分 **内容社区**（Blog + Forum）
- [ ] 拆分 **关于我们**
- [ ] 保留 **营销门户** 作为主应用（或最后拆分）

### Phase 4 — 独立部署（持续）
- [ ] 每个子应用独立 CI/CD 流水线
- [ ] 基座应用自动发现远程模块版本

## 四、风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 共享依赖版本不一致 | 高 | 基座统一锁定 vue/vue-router 版本，子应用使用 `external` |
| 跨应用样式泄漏 | 中 | 继续使用 CSS Modules，基座提供 Design Token 共享包 |
| 路由状态同步 | 中 | 基座管理顶层路由，子应用使用 `memory` history 模式 |
| 弹窗/浮层层级冲突 | 中 | z-index 体系由基座统一管理，子应用通过事件通知基座挂载 |
| 构建复杂度上升 | 中 | 提供本地开发代理配置，子应用可独立运行 |

## 五、决策建议

**不建议立即全面微前端化**。当前项目规模（333 个前端文件）尚未达到微前端的收益拐点。

**建议触发条件**（满足任一即启动）：
1. 前端团队 > 10 人，多人协作冲突频繁
2. 构建产物 vendor chunk > 300KB gzip
3. 新增独立业务线（如海外版、企业定制版）
4. 需要不同技术栈的子系统（如 3D 可视化、数据大屏）

**当前最佳实践**：保持 Manifest 系统的插件化扩展能力，作为微前端的预备接口；当条件触发时，Manifest 可直接升级为远程模块加载器。
